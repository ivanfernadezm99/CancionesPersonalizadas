# Exploration — Suno Tag Validation (artist names in reference_song)

**Date**: 2026-08-11
**Project**: cancionespersonalizadas
**Scope**: Prevent Suno API rejections caused by artist names reaching the `style`/`prompt` tags.

## Current State

### The reported failure

A user typed "los palmeras" in the `reference_song` field. That string is injected verbatim into the
voice prompt as ` Inspirada en el estilo de {reference_song}.` and sent to Suno's
`POST /api/v1/generate` in **both** the `prompt` and `style` fields. Suno rejects the request:

> "Your tags contain artist name los palmeras - we don't reference specific artists on Our, please change your tags and try again."

The rejection happens at invoke time (before generation), so no credits are lost, but the job fails
and the user must redo the whole preview flow.

### Complete data flow (user input → Suno API)

```
Frontend create form (free text, maxlength 200)
  └─ POST /api/projects          → SongProjectCreate (reference_song, max 200, NO content validation)
       └─ projects.store.create_project → projects.reference_song (SQLite)
Frontend preview page → POST /api/projects/{id}/preview
  └─ create_preview_job (app/projects/__init__.py:59)
       └─ metadata["reference_song"] = project.reference_song   (also for /final)
       └─ asyncio.create_task(project_worker(job_id))
            └─ project_worker (app/projects/__init__.py:200)
                 ├─ lyrics_generate(reference_song=<RAW>)   → app/lyrics/prompts.py:136
                 │     "Referencia musical: {reference_song}. Inspírate en el estilo musical..."
                 │     (LLM may echo the artist name into the generated lyrics → Suno `lyrics` field)
                 ├─ voice_prompt = build_prompt(reference_song=<RAW>)  → app/voice/__init__.py:76
                 │     prompt += " Inspirada en el estilo de {reference_song}."
                 └─ music_generate(lyrics, voice_prompt)    → app/music/__init__.py:73
                      └─ SunoProvider.generate()            → providers.py:148
                           └─ _invoke(lyrics, prompt)       → providers.py:190
                                payload = { "prompt": prompt, "style": prompt, "lyrics": lyrics, ... }
                                POST {SUNO_BASE_URL}/api/v1/generate   ← ARTIST NAME LANDS HERE (both fields)
```

Cover mode (`reference_audio` present) uses `POST /api/v1/generate/upload-cover` with
`{"style": prompt, "prompt": lyrics}` — the voice prompt still carries the artist name in `style`.

### Fields that can carry artist names

| Field | Path to Suno | Risk |
|-------|-------------|------|
| `reference_song` | `style`+`prompt` (text-to-music) / `style` (cover), via `build_prompt`; also into lyrics LLM prompt | **HIGH — this is the reported bug** |
| `genre` | `build_prompt` → style tags (free text via API, but frontend uses a fixed `<select>`) | LOW via UI; MEDIUM via direct API |
| `mood` | `build_prompt` → style tags (same) | LOW via UI |
| `idea` / `story` / fragments | Only into lyrics LLM prompt → generated lyrics → Suno `lyrics`/`prompt` | MEDIUM (indirect — LLM could echo an artist name into the lyrics) |
| `recipient` | Into lyrics only | LOW (unless recipient name coincides with an artist name, e.g. "Shakira") |
| `reference_description` | Voice prompt (takes precedence over `reference_song` in `build_prompt`) | LOW (auto-generated by audio analysis) |

Note: in the **project** flow, `project_worker` passes the raw `reference_song` to `lyrics_generate`
even when `reference_description` is present (app/projects/__init__.py:240), while the **legacy
job** flow uses `reference_song=ref_desc or ref_song` (app/jobs/worker.py:60). The two paths are
inconsistent.

## Suno API Restrictions (documented)

- **Authoritative evidence**: the production error message itself — sunoapi.org (the Suno REST
  gateway this project uses, `SUNO_BASE_URL=https://api.sunoapi.org`) rejects any request whose
  tags contain an artist name. The rejection is a business-code error returned with HTTP 200 and
  `code=400` (handled in `_invoke`, providers.py:246-250).
- **Matching is case-insensitive substring matching**: the error echoes "los palmeras" for input
  "Los Palmeras" — Suno normalizes case and likely matches a known-artist database.
- **Suno's terms of service** (fetched 2026-08-11) prohibit infringing third-party IP and
  impersonating artists; Suno's moderation layer enforces "don't reference specific artists" in
  custom mode, which is what this gateway surfaces.
- There is **no local artist database** in this repo — no blocklist, no sanitizer exists today
  (grep for `sanitize|blocklist|artist` in `app/` finds nothing relevant).

## Existing Error Handling — What the User Sees Today

1. `_invoke` raises `SunoError("Suno invoke rejected (code=400): Your tags contain artist name ...")`
   (providers.py:250).
2. `project_worker` catches it in the generic `except Exception`, logs it, and sets the job status
   to `failed` with `error=str(exc)` (app/projects/__init__.py:349-357) — the **raw English Suno
   message** is persisted.
3. Frontend `preview.component.ts` polls `GET /api/status/{job_id}` (main.py:216 → `JobStatusResponse.error`);
   on `status === 'failed'` it rejects with `new Error(status.error)` and renders the raw English
   message in the error state with a "Reintentar" button. Same pattern in `download.component.ts`.
4. `build_prompt` also raises `ValueError` on unknown voice — the established validation precedent
   is Pydantic field validators returning 422 (`_validate_voice`, models.py:10; song-projects spec
   RQ-PRJ-01 "THEN response MUST be 422").

## Edge Cases

| Input | Suno outcome | Local detection feasibility |
|-------|-------------|----------------------------|
| `los palmeras` (lowercase) | Rejected (case-insensitive) | Blocklist/DB needed |
| `Los Palmeras` (title case) | Rejected | Blocklist/DB needed |
| `Grupo Los Palmeras` | Rejected (contains artist substring) | Blocklist/DB needed |
| `Bailando - Enrique Iglesias` | Rejected (artist in tags) | Strippable: keep "Bailando" |
| `Bachata Rosa - Juan Luis Guerra` | Rejected | Strippable: keep "Bachata Rosa" (⚠️ this is the canonical example in `models.py` docstrings AND the test fixtures) |
| `Despacito` / `La Bamba` (song only) | Likely accepted | No action |
| `una canción triste de los 90` (description-like) | Likely accepted | No action |
| Legacy project already stored with artist name | Rejected at generation | **Input validation won't catch this** — needs generation-time guard |

Important: the frontend hint text (`Ej: "Bailando" de Enrique Iglesias, "Despacito", "La Bamba"`),
the `reference_song` docstrings, and test fixtures (`test_voice_prompt.py`, `test_full_flow.py`
"El Amor - Tito La Rosa", `test_projects_orchestrator.py`) **all promote the song-artist format
that Suno rejects**. The examples themselves would fail against Suno today.

## Where Validation/Sanitization Is Most Effective

1. **Input time (Pydantic validator on `reference_song` in `SongProjectCreate` + `SongProjectUpdate`)**
   — fails fast with 422 and a friendly message; consistent with the existing `_validate_voice`
   pattern. Does NOT protect legacy projects already in SQLite.
2. **Generation time (project_worker / `build_prompt` / `SunoProvider._invoke`)**
   — sanitizes the tags for legacy projects and any path that bypasses input validation. This is
   the only layer that covers already-stored projects.
3. **Error translation** — detect the Suno artist-rejection message and surface a friendly Spanish
   error ("El nombre de la canción contiene un artista; quitá el nombre del artista y probá de
   nuevo") as a safety net for anything local detection misses. Suno's matching is opaque, so a
   purely local heuristic can never be 100% accurate.
4. **Frontend** — fix the hint text (it currently *teaches* users to type artist names), optionally
   client-side strip of `- artist` patterns, and surface the translated error.

## Approaches

1. **Strip heuristic + friendly error fallback** (recommended)
   - Parse `reference_song` to drop artist parts (`"Song - Artist"`, `"Song de Artist"`,
     `"Song (Artist)"` → keep the song token) at input time; reject pure-artist-looking input
     (unparseable after strip) with a 422.
   - Sanitize again at generation time (`build_prompt` or `SunoProvider._invoke`) to protect
     legacy projects.
   - Detect the Suno artist-rejection error and translate it to Spanish for the job `error` field.
   - Pros: fails fast for the common case, protects legacy data, gives a clean UX safety net.
   - Cons: heuristic strip can't catch band names typed alone ("Los Palmeras"); may need a small
     curated blocklist for popular Argentine artists (Los Palmeras, La Mona Jiménez, etc.).
   - Effort: Medium.

2. **Input-time rejection only (Pydantic 422)**
   - Add a `field_validator("reference_song")` that rejects known artist patterns; no generation
     changes.
   - Pros: smallest diff; consistent with `_validate_voice`; existing tests show the 422 pattern.
   - Cons: leaves legacy projects broken; still needs a detection mechanism; any miss still
     surfaces the raw English Suno error.
   - Effort: Low-Medium.

3. **Suno-only sanitization in `SunoProvider._invoke()`**
   - Strip artist names from the prompt/style payload just before sending; OpenClaw keeps the
     rich prompt.
   - Pros: zero impact on the OpenClaw path; single choke point for Suno.
   - Cons: silent behavior change (user's input is silently altered); doesn't fix the lyrics path;
     Suno matching is opaque so misses are still possible; no improvement to today's raw-error UX.
   - Effort: Low.

4. **Error translation only**
   - Map the Suno artist-name error to a friendly Spanish message in the worker/status path.
   - Pros: immediate, tiny fix; improves today's UX.
   - Cons: does not prevent the failure — user still has to redo the flow every time.
   - Effort: Low.

## Recommendation

Combine **1 (strip + friendly error)** with a generation-time guard and error translation:
- Input-time validation/sanitization of `reference_song` (create + patch) with a clear 422 message.
- Generation-time sanitization in `build_prompt` (or `SunoProvider._invoke`) so **legacy projects**
  stored before the fix are covered.
- Error translation in the job-failure path so anything missed by local heuristics produces a
  friendly Spanish message instead of raw English Suno output.
- Frontend: fix the hint text and add the same strip/validation client-side.

## Risks

- **No local artist database**: Suno's matching is a private, case-insensitive, substring-based
  database. Local heuristics + a small curated blocklist can cover the reported case and common
  Argentine artists, but will never be exhaustive — the error-translation safety net is essential.
- **Existing tests and examples embed the "song - artist" format** (`test_voice_prompt.py`,
  `test_full_flow.py`, `test_projects_orchestrator.py`, `models.py` docstrings, frontend hint).
  Fixtures asserting a 201 on `"Bachata Rosa - Juan Luis Guerra"` will need updating if input
  validation rejects that string.
- **Legacy projects**: validation at input alone leaves already-stored `reference_song` values
  vulnerable — generation-time sanitization is required.
- **Two worker paths differ**: `project_worker` always passes raw `reference_song` to lyrics;
  `job_worker` passes `ref_desc or ref_song`. Any sanitization must be applied consistently in both
  (or centralized in `build_prompt` + `lyrics` prompt builder).
- **Out of scope but discovered**: `.env.docker` contains a committed `SUNO_API_KEY` (secret leak,
  not part of this change).

## Ready for Proposal

Yes. Recommended change: `suno-tag-validation` — validate/sanitize `reference_song` (input +
generation), translate the Suno artist-rejection error, and update frontend hint text. Orchestrator
should note that existing test fixtures and docstrings promote the rejected format and will need
updating.
